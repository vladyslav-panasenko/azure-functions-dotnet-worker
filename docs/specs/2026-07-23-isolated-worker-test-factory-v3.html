Goal

Implement an upstream-ready package named Microsoft.Azure.Functions.Worker.Testing that starts the application entry point in the test process, replaces only the host transport, preserves the production worker startup and invocation pipeline, supports service/configuration overrides, and exposes function-targeted HTTP and generic invocation APIs. Implement an ASP.NET Core companion package for ConfigureFunctionsWebApplication(). Microsoft naming, signing, publishing, and support remain upstream release decisions. The factory is a worker integration test host, not an Azure Functions runtime emulator.

Success criteria

  • A test using FunctionsApplicationFactory<Program> executes the real application registrations, generated function executor, converters, worker middleware, scoped DI, serializer, output-binding middleware, cancellation, logging, and disposal without func.exe, a child process, or an open TCP port.
  • CreateHttpClient(functionName) exercises a selected built-in-model HTTP function without simulating host routing; WithAspNetCore().CreateClient() exercises the worker-owned ASP.NET Core endpoint pipeline through TestServer, including typed route values and IActionResult/IResult.
  • InvokeAsync(functionName, request) supports non-HTTP protocol values without pretending to run trigger listeners; duplicate, missing, cancellation, exception, output, and disposal paths are deterministic.
  • A transport suite compares the in-memory channel with a loopback gRPC transport over the same worker messages, while a bounded differential suite compares supported user-visible HTTP and queue fixtures with the repository's Core Tools E2E path; unexplained differences block release.
  • Median warm invocation overhead is below 5 ms for a no-op function and factory startup is below 500 ms on the repository's hosted Windows and Linux CI agents, reported rather than enforced until two stable releases establish variance.

Non-goals

  • Reimplementing the Azure Functions host, trigger listeners, scale controller, host locks, function keys, EasyAuth, extension bundles, retry scheduling, checkpointing, or cloud services.
  • Claiming that a synthetic Queue, Service Bus, Blob, Event Hubs, Cosmos DB, or Durable invocation proves service/host integration.
  • Replacing Core Tools, Aspire, emulators, Testcontainers, or deployed smoke tests for full-system coverage.
  • Shipping service-specific fake packages in the first release.
  • Reproducing built-in-model host URL routing, route precedence, authorization, or function-key behavior; core HTTP tests target a function by name.
  • Publishing packages under Microsoft ownership, updating upstream issues, or claiming Microsoft support without a separate product-owner authorization.

Relationships

  • One factory owns one application host and one in-memory protocol session; it may create many clients and invocations.
  • One invocation has one function definition, one invocation ID, zero or more input values, optional trace/retry context, and zero or more output values.
  • The transport lane compares two transports over one worker contract; the runtime lane compares only declared user-visible observations with Core Tools.

Proposed design

The factory installs an internal AsyncLocal-backed application-assembly scope and then runs the real application entry point through a repository-owned adaptation of the generic-host resolver used by ASP.NET Core testing. The scope is visible while modern FunctionsApplicationBuilder eagerly executes generated startup and is removed in finally after host capture; it never uses process-global environment state. At host-building time the factory applies test configuration and replaces the gRPC client factory with a signed friend implementation. A minimal in-memory Functions host speaks the existing streaming-message state machine to GrpcWorker, requesting metadata, loading the exact returned definitions, invoking/cancelling functions, and correlating responses. This preserves InvocationHandler as the only execution path. Built-in HTTP is function-targeted because URL routing is host-owned. The ASP.NET companion is explicitly enabled with WithAspNetCore() and replaces worker-side Kestrel with TestServer.

Feasibility conclusion: Yes, this is implementable in the worker repository. The leading community framework demonstrates breadth, while the historical maintainer branch and current seams show a smaller official design can avoid reflection. The design is not a replacement for the Azure Functions host.

T01
Make application identity explicit during startup
Not Started

Outcome: Generated metadata/executor and extension startup run against the function assembly even when modern builder initialization occurs before host capture, without changing ordinary application behavior.

Observed current state: FunctionsApplicationBuilder eagerly runs callbacks in its constructor; InvokeAutoGeneratedConfigureMethods() and RunExtensionStartupCode() use Assembly.GetEntryAssembly(), which remains the test runner when the function entry point is invoked reflectively.

Inputs, preconditions, and outputs: Input is Assembly applicationAssembly or an internal scoped override; precondition is a non-null executable function assembly and flowed execution context; output is one-time registration of generated startup and extension startup for that assembly.

Depends onNone
UncertaintyMedium — the eager-startup fact is observed, but the new scoped seam needs parallel and suppressed-flow proof.
OwnerWorker hosting owner
Downstream outputAssembly resolver, overloads, and friend seam consumed by T03.

Steps

  1. Add internal WorkerApplicationAssemblyContext in Core using AsyncLocal and a disposable Push(Assembly); allow nested identical scopes, reject different nested assemblies, and restore the prior value in Dispose().
  2. Add public InvokeAutoGeneratedConfigureMethods(IHostBuilder, Assembly); make the parameterless overload use the scoped assembly when present and otherwise preserve Assembly.GetEntryAssembly().
  3. Add internal AddFunctionsWorkerCore(IServiceCollection, Assembly, Action<WorkerOptions>?); move extension-startup discovery into an assembly-taking helper and make the existing public overload use the same resolver. Do not add another public service-collection overload.
  4. Make duplicate startup for the same assembly idempotent through an assembly-keyed builder/service marker, while two different assemblies in one host fail before partial registration.
  5. Grant the signed testing package friend access to the Core scope/internal overload and add XML docs plus null, nesting, parallel, suppressed-flow, duplicate, explicit, legacy, and compile-compatibility tests.

  • PII/data retention: Captured bodies/logs exist in memory for the factory lifetime and are not written unless the test runner or caller exports them. Failure formatting truncates payloads by default.
